Spec 008 — Task 7 Benchmark Comparison
======================================

Machine
-------
AMD Ryzen 7 PRO 7840U w/ Radeon 780M Graphics, linux/amd64, go1.26.5.
Otherwise idle. Both baseline.txt and new.txt were measured on this machine;
a comparison across two machines measures the machines.

Baseline: b5e8a55 (pre-implementation)
After:    67bd978 + Task 8 revert
Method:   go test -bench=. -benchmem -count 5 ./..., compared with benchstat.

All latency and allocation figures below are MemStore numbers. MemStore is the
only Store in this repo. The work this spec removes is on the read side, so on
a durable store the remaining write transaction — page allocation and fsync —
sets the floor and the end-to-end improvement is materially smaller. Do not
read these as production promises (§2.7).

These numbers are for the tree AFTER Task 8 reverted the two geometry changes.
The revert cost nothing: measured against the pre-revert tree, every benchmark
moved within noise (geomean -0.96%, all comparisons p > 0.05). Details in
geometry_delta.txt.

Shortfalls, stated plainly
--------------------------

1. Batch throughput: 1.28x-2.75x, against a >=5x target.
   The target was set believing serialization dominated the batch. It does not.
   CBOR and the collect-phase geometry took the serialization and vector cost
   out — visible as -60.4% collect bytes and -34% BatchFacets/F1 B/op — but the
   remaining time is clustering and maintenance, which this spec never touched.
   5x was not reachable by the changes this spec contains. Reaching it means
   attacking the clustering pass, which belongs to its own spec.

2. The distance target is met and moot.
   CosineDistanceUnit is 39x CosineDistance at 1536 dimensions, far past the
   >=2x target, and that number is real. It buys nothing here. Every call site
   the spec moved onto it measures a PROJECTED vector, which is not unit, and
   making those vectors unit moved every cluster boundary in the corpus (§2.5).
   Task 8 moved them all back. The pair ships correct, tested, benchmarked, and
   uncalled. The 39x also explains itself: gonum ships amd64 assembly for the
   dot product but runs a pure Go scalar loop for Nrm2, so removing the two norm
   passes removed nearly all of the cost.

3. findNearestStories still allocates.
   The store reads and decodes are gone, which was the point. What remains is a
   `cands` staging slice, materialized only to shorten the RLock hold, sized to
   the active story population on every call. This is the direct cause of the
   one regression in the suite:

     IngestDuringApply   634.5ns -> 835.7ns  (+32%)
                         136 B/op -> 417 B/op  (+207%)
                         6 allocs/op -> 9 allocs/op  (+50%)

   The old path read this metadata from the store under the write lock; the new
   path copies it out of the index. Cheaper in absolute terms on the steady-state
   path (which is 213x faster), more expensive on this one narrow benchmark that
   measures Ingest latency while a batch holds the lock. The fix is to hold the
   RLock across the distance loop, or to filter and score in one pass without
   staging. Not done here; recorded.

4. Allocation counts vs allocation bytes.
   Two targets say "allocations" without saying which. Both are met on bytes and
   missed on count. The changes replaced many small allocations with fewer large
   ones and removed vector copies; bytes is the measure that tracks what was
   changed. Recorded both ways rather than picking the flattering one.


Peak batch heap
---------------
No transient copy of the collected set: projection is in place via
geom.ProjectInPlace; corpusMeanOf and projectAll are gone. Resident cost is
facets x dim x 4 bytes plus payload-free overhead. At the collect fixture size
(400 signals x 3 facets x 256 dim) the collect phase allocates 4.14 MB per run,
down from 10.45 MB.
